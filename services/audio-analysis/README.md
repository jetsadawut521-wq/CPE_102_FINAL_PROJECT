# วิเคราะห์ไฮไลท์จากเสียง (ทดลอง)

ค่าเริ่มต้นใหม่เป็น **fast**: เปรียบเทียบรูปแบบเสียงซ้ำ ไม่ใช้ Demucs, Torch,
NATTEN หรือโมเดลที่ต้องดาวน์โหลดเพิ่ม ใช้ numpy/scipy และ FFmpeg ที่ติดตั้งไว้แล้ว
ตัวเล่นและเสียงที่ผู้ใช้ได้ยินยังมาจาก YouTube IFrame แบบเดิม
ไม่มีการบันทึกไมโครโฟนหรือขอแชร์แท็บ

**ผลโหมดเร็วคือ “ท่อนซ้ำที่อาจเป็นฮุค” ไม่ใช่การยืนยันว่าเป็นฮุค**
ท่อน verse/pre-chorus ก็อาจซ้ำได้ และเพลงที่เปลี่ยนเรียบเรียงหรือร้องต่างกันมากอาจตรวจไม่พบ
ไม่อนุมานว่า instrumental break เป็น dance-break

## ผู้ใช้ที่ติดตั้งตามขั้นตอนเดิมแล้ว

อัปเดตแพ็กเกจสำหรับตัววิเคราะห์แถวครั้งแรก แล้วเปิด worker ใหม่ใน Ubuntu (YOLO ต้องติดตั้งเพิ่มแยกจากตัววิเคราะห์เสียง):

```bash
cd /mnt/c/Users/NatNuay/Downloads/my-app-personal/services/audio-analysis
source .venv/bin/activate
python -m pip install -r requirements-fast.txt
python -m pip install -r requirements-formation-yolo.txt
cd ../..
python services/audio-analysis/server.py
```

ถ้าเก็บโปรเจกต์ไว้ที่อื่น เปลี่ยน cd ให้ตรงโฟลเดอร์
ใน VS Code บน Windows เปิดโฟลเดอร์เดียวกัน เพิ่มใน `.env.local`:

```dotenv
AUDIO_ANALYSIS_URL=http://127.0.0.1:8765
```

แล้ว `npm run dev` และเปิด http://localhost:3100
เปิดทั้งสองหน้าต่างทิ้งไว้ เว็บเริ่มงานเมื่อเลือกคลิป ไม่ต้องกดวิเคราะห์
ตรวจบริการจาก PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health
```

ต้องขึ้น version `fast-experiment-v3` และ engine `fast`
ถ้าเคยตั้ง `AUDIO_ANALYSIS_ENGINE=full` ไว้ ให้เปลี่ยนเป็น fast แล้วเปิดบริการใหม่

## ติดตั้งเฉพาะโหมดเร็วบนเครื่องใหม่

ต้องมี Python 3.11, FFmpeg, Node.js สำหรับเว็บ และเครื่องมือ Node.js/Deno ตามความจำเป็นของ yt-dlp
ไม่จำเป็นต้องลงชุดโมเดลหนัก:

```bash
cd services/audio-analysis
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-fast.txt
cd ../..
python services/audio-analysis/server.py
```

## แผนผัง formation แบบปรับเทียบพื้นเวที

ตั้งใจทำ workflow นี้ตามแนวคิดของ [GridStage](https://github.com/ChangShengHsun/GridStage):
หยุดคลิปที่เห็นพื้นเวทีชัด กด **ตั้งค่าพื้นเวที (4 จุด)** แล้วคลิกมุมไกลซ้าย → ไกลขวา → ใกล้ขวา → ใกล้ซ้าย
จากนั้นกด **วิเคราะห์แถวทั้งคลิป** ระบบใช้ YOLO26s-pose ตรวจจับคนหลายคนและ keypoints ของ COCO ในแต่ละเฟรมตัวอย่าง
โดยใช้ตำแหน่งข้อเท้า (หรือหัวเข่า/สะโพกเมื่อข้อเท้ามองไม่ชัด) ประมาณจุดยืน ก่อนแปลงพิกัดด้วย perspective transform จากมุมทั้งสี่
จำนวนเป้าหมายเลือกจากจำนวนคนที่ตรวจพบได้บ่อยที่สุดตลอดคลิป (หากเสมอกันจึงเลือกจำนวนที่มากกว่า)
และตัด detection คะแนนต่ำเข้มขึ้น เพื่อลดจุดซ้ำจากการบังกัน ทั้งนี้หากมุมกล้องหรือการบังทำให้ตัวตรวจจับเห็นผิดซ้ำๆ จำนวนก็ยังคลาดเคลื่อนได้
ตำแหน่งเท้าที่อยู่นอกพื้นที่สี่เหลี่ยมที่ปรับเทียบจะไม่ถูกนับ ช่วยกันภาพสะท้อนจากกระจกที่อยู่นอกพื้นที่เวที
ระบบใช้ค่าแถวหลังแปลงพื้นเพื่อแยกช่วงที่ตำแหน่งกลุ่มเปลี่ยนจริง และแสดงจุดสีเดิมตามคนใน timeline

วิดีโอยังเล่นต่อได้ระหว่างประมวลผล ไฟล์วิดีโอและเฟรมชั่วคราวถูกลบเมื่อเสร็จ
แคชผลแยกตามคลิปและมุมที่ตั้งไว้เพื่อไม่เอาผลจากกรอบพื้นคนละชุดมาใช้ซ้ำ
worker ใช้จำนวน CPU threads ที่มีในระบบ สูงสุด 6 เธรด เพื่อเร่งการวิเคราะห์บน CPU
แต่เวลาประมวลผลยังขึ้นกับความยาวคลิปและความเร็วเครื่อง/เครือข่าย
แพ็กเกจ PyTorch มีขนาดใหญ่ และไฟล์โมเดลจะดาวน์โหลดอัตโนมัติเมื่อวิเคราะห์ formation ครั้งแรก
การปรับเทียบช่วยแก้แกนลึกและมุมมองพื้นเวที แต่ยังไม่รับประกันว่าตัวตรวจจับจะเห็นนักเต้นครบทุกเฟรม

แนวทาง floor calibration อ้างอิง workflow ของ GridStage (MIT); โค้ดวิเคราะห์ Muverse ใน branch นี้เขียนแยก
ใช้การจับคู่ตำแหน่ง/สีเพื่อรักษา ID ของคนระหว่างเฟรม และคงตำแหน่งล่าสุดเมื่อคนหายไปชั่วคราว;
ถ้าคนไม่ปรากฏพร้อมกันในเฟรมใดเลย ระบบยังอาจนับจำนวนสมาชิกทั้งหมดไม่ครบ
ต้องมี FFmpeg และ worker ใน Ubuntu/WSL เปิดค้างเหมือนบริการวิเคราะห์เสียง

หลังวิเคราะห์เสร็จ ตัวเล่นเลือกแก้ formation ทุกแถวใน timeline ได้: เลือกแถวจากรายการ ลากจุดบนแผนผัง ใส่ชื่อนักเต้น แล้วกดบันทึก การแก้ไขและ calibration เก็บใน localStorage ของเบราว์เซอร์แยกตาม video ID; ดูขั้นตอนติดตั้งและใช้งานแบบครบได้ที่ [คู่มือส่งต่องาน](../../docs/DEVELOPER_GUIDE.md).

Random Dance ใน playlist ใช้คลิปที่มีทั้งผลไฮไลท์และ formation timeline ที่บันทึกแล้วเท่านั้น และโหลด formation ของ video ID ที่กำลังเล่นมาประกบ ตัวแก้ไข formation ของ Muverse เขียนแยก โดยอ้างอิง workflow ของ [GridStage](https://github.com/ChangShengHsun/GridStage); ไม่ได้คัดลอก source code ของ GridStage.

## ขั้นตอนและเป้าหมายความเร็วของเสียง

1. yt-dlp ดึง audio stream ของคลิปเดิมลงไฟล์ชั่วคราว โดย fast ไม่สร้าง WAV เพิ่ม
2. FFmpeg ถอดรหัสเป็น mono 8 kHz ในหน่วยความจำ เฉพาะเพื่อวิเคราะห์ ไม่เปลี่ยนเสียงตัวเล่น
3. scipy/numpy คำนวณลักษณะเสียงทุก 0.25 วินาที แล้วเทียบช่วงซ้ำและจุดเปลี่ยนโครงสร้าง
4. ส่งช่วงที่มีหลักฐานซ้ำหลายรอบ พร้อมป้ายทดลอง ถ้าไม่มีหลักฐานก็ไม่สร้างช่วงขึ้นมา

เป้าหมายคือผลหลังเปิดคลิปไม่เกิน 30 วินาที รวมคิว/ดาวน์โหลด/API/UI
**ยังไม่มีผลทดสอบคลิป YouTube จริงครบวงจรบนเครื่องผู้ใช้ว่าเข้าเกณฑ์นี้**
การทดสอบเสียงสังเคราะห์ยาว 152 วินาทีให้ช่วงซ้ำ 3 รอบตรงกับจุดที่สร้างไว้
ขั้นคำนวณใช้ประมาณ 0.1 วินาทีบนสภาพแวดล้อมทดสอบ ไม่รวม YouTube/ถอดรหัส
ตัวเลขนี้ไม่ใช่การรับประกันเวลาและความแม่นยำของเพลงจริง

โหมดเร็วจำกัดงานรวมประมาณ 27 วินาที (รวมเวลาคิว), ดาวน์โหลด 20 วินาที,
ถอดรหัส 8 วินาที เว็บถามสถานะทุก 2 วินาทีและหยุดรอเมื่อเกินประมาณ 30 วินาที
การหมดเวลาเป็นผลไม่สำเร็จ ไม่ถือว่าทำตามเป้าหมายความเร็วสำเร็จ
งานที่ไม่ได้ถามสถานะนาน 8 วินาทีจะหยุด/ข้าม เพื่อลดคิวจากคลิปเก่า

## การเก็บข้อมูลผลไฮไลท์

- ไม่บันทึกผลวิเคราะห์เสียงลงแคชถาวร ทุกการประมวลผลใหม่วิเคราะห์เสียงอีกครั้ง
- ตอนเริ่ม worker จะลบไฟล์ผลเสียงเดิม (`fast-repeat-*` และ `fold0-v1-*`) ใน cache directory
- เก็บสถานะ/ผลชั่วคราวใน RAM ระหว่าง polling และล้างรายการที่เสร็จหลัง 5 นาที
- ผลแผนผังแปรแถวยังแคชแยกตามการตั้งค่าของฟีเจอร์นั้น
- chapter ของผู้อัปโหลดและคอมเมนต์ที่ระบุช่วง chorus พร้อมขอบเขตชัดเจนเป็นแหล่งหลักได้
- คอมเมนต์ที่เป็นเพียงประโยครีแอ็กชันไม่สร้างขอบเขต แม้มี timestamp; label ของ verse/pre-chorus/ท่อนอื่นจะไม่ถูกเสนอเป็นฮุค
- ไฟล์ดาวน์โหลด/ข้อมูลชั่วคราวถูกลบหลังจบ ยกเลิก หรือหมดเวลา
  ไม่ลบไฟล์นอกโฟลเดอร์ชั่วคราวของงาน
- ไม่ดาวน์โหลดไฟล์น้ำหนักโมเดลเพิ่มใน fast และไม่สร้าง WAV บนดิสก์เพิ่ม
  แต่การลบไฟล์ใน WSL ไม่ได้ทำให้ไฟล์ดิสก์เสมือนของ Ubuntu ย่อคืนพื้นที่ Windows ทันที

## ขอบเขตและการเชื่อมต่อ

- บริการ bind เฉพาะ 127.0.0.1:8765 (เปลี่ยนด้วย AUDIO_ANALYSIS_PORT)
- ถ้าต้องข้ามเครื่อง ต้องมี reverse proxy HTTPS และ AUDIO_ANALYSIS_TOKEN ทั้งสองฝั่ง
  ไม่เปิด Python port ต่อสาธารณะโดยตรง
- ก่อนเปิดเว็บสาธารณะต้องมี authentication/rate limiting ระดับ deployment เพิ่ม
  คิวจำกัดไม่ได้ป้องกันการใช้งานผิดวัตถุประสงค์ครบชุด
- WSL2 ปกติเชื่อมจาก Windows ไป Linux ผ่าน localhost ได้
  ถ้า health ติดต่อไม่ได้ ให้ตรวจ localhost forwarding ก่อนเปลี่ยน bind
- ทำงานทีละ 1 คลิป รอได้ไม่เกิน 8 งาน เก็บสถานะใน RAM ไม่เกิน 128 รายการ
- รับคลิปไม่เกิน 15 นาที ไม่รับ live จำกัดไฟล์ 100 MB เมื่อ yt-dlp ตรวจขนาดได้
- YouTube อาจบล็อกการดึงเสียงได้ ไม่ข้ามข้อจำกัดเครือข่าย/ล็อกอินอัตโนมัติ
- ใช้กับคลิปที่มีสิทธิ์ดาวน์โหลดและวิเคราะห์ และตรวจเงื่อนไขแหล่งข้อมูล
- ต้องเป็น process ที่รันต่อเนื่อง ไม่ใช่ Next.js serverless อย่างเดียว

## กลับไปใช้โมเดลเดิม (full)

เฉพาะเครื่องที่ติดตั้ง All-In-One/Demucs/NATTEN ตาม upstream ครบแล้ว:

```bash
AUDIO_ANALYSIS_ENGINE=full python services/audio-analysis/server.py
```

Full ใช้ harmonix-fold0 บน CPU ตามค่าเดิม จำกัด 180 วินาที ไม่อยู่ในเกณฑ์เร็ว 30 วินาที
ใช้ AUDIO_ANALYSIS_THREADS ปรับจำนวนเธรด (ค่าเริ่มต้นไม่เกิน 6 ตาม CPU ที่จัดสรร)
AUDIO_ANALYSIS_DEVICE=cuda ต้องมี NVIDIA GPU กับ PyTorch/NATTEN ที่รองรับ CUDA จริง
AMD Radeon 840M ของเครื่องผู้ใช้ใช้ CUDA ของชุดนี้ไม่ได้โดยตรง
ไม่ควรติดตั้ง CUDA package เพื่อหวังให้ AMD GPU ใช้โมเดลนี้ได้

ผล full ที่ผู้ใช้รายงานสำหรับ ZovUnDFt0wI:
แยกเสียง 100.45s, เตรียมข้อมูล 2.56s, โหลดโมเดล 0.55s, inference 51.39s, รวม 164.1s
นี่คือเหตุผลที่ทดลอง detector เบาแทน การเปลี่ยน timeout/แคชไม่ทำให้คลิปใหม่ผ่านเกณฑ์
progress bar ของ All-In-One แสดงแค่ช่วง inference ไม่ใช่เวลารวมทั้ง pipeline

โมเดล full มีข้อกำหนด license แยกจากโค้ด เช่น madmom models ระบุ non-commercial
ตรวจใบอนุญาต dependencies/models ก่อนใช้งานเชิงพาณิชย์

## การปรับความทนต่อจุดเริ่มท่อนที่คลาดเล็กน้อย (v2)

เพิ่มความละเอียดเวลาเป็น 0.25 วินาที และยอมให้การเทียบรูปแบบขยับได้ไม่เกิน 0.25 วินาที
เริ่มด้วยเกณฑ์ความคล้าย 0.78 และระยะเวลาขั้นต่ำ 12 วินาที หากไม่พบคู่ซ้ำจะลองซ้ำหนึ่งรอบที่ 0.68
โดยยังต้องพบช่วงที่เข้าคู่กันอย่างน้อยสองตำแหน่ง และยังกรองช่วงเงียบ/ช่วงที่พลังเสียงต่ำออก
ทดสอบเสียงสังเคราะห์ที่ท่อนซ้ำเริ่มเยื้อง 0.125/0.25/0.375 วินาที แล้วตรวจต้น–ท้ายช่วง
รวมกรณีเสียงคงที่ เงียบ และทำนองสุ่มที่ไม่ควรถูกระบุเป็นท่อนซ้ำ
ยังไม่ยืนยันว่าการปรับนี้แก้คลิปจริงที่ผู้ใช้รายงานว่าหาไม่พบ ต้องใช้ตัวอย่างจริงตรวจเพิ่ม

ไม่มีการแคชผลวิเคราะห์เสียงแบบถาวร การเรียกใหม่จะวิเคราะห์จากไฟล์เสียงชั่วคราวอีกครั้ง
บรรทัด `[audio] ... fast summary {...}` แสดงสรุปเหตุที่ไม่พบ/จำนวนคู่รูปแบบเสียงที่ผ่านเกณฑ์
เพื่อใช้ตรวจกรณีที่ไม่มีไฮไลท์ โดยไม่เก็บหรือแสดงไฟล์เสียง

## คอมเมนต์ชมท่อนเพลงไม่ใช่ขอบท่อนเพลง

คอมเมนต์ของ Don’t Wanna Cry Front Ver. (aJ55DJE4Os4) ที่รายงานจริงมีข้อความ
`2:12-2:17 i love this part of the chorus` อยู่ในรายการจุดที่คนดูชอบ
ไม่ใช่ตาราง section จึงห้ามแปลงเป็น chorus เริ่ม 132 จบ 137 วินาที
ผู้ใช้อัปโหลดเสียงและระบุฮุคแรก 58–79 วินาที; หลังปรับต้นท่อนพบ 58.5–79.25 วินาที
ทดสอบกับ features ที่ได้จากไฟล์จริง โดยไม่ใช้คอมเมนต์กำหนดขอบและไม่ฝังเวลาเฉพาะเพลง

ใช้ชื่อ section แบบเป็นป้ายโดยตรง (chorus 1, first chorus, ท่อนฮุคแรก ฯลฯ)
และแยกจากประโยคความคิดเห็น แม้มีคำว่า chorus หรือเป็นช่วงเวลาก็ไม่ได้ยืนยันขอบ
การจัด offset ไม่ใช้จุด chorus โดด ๆ จากคนละคอมเมนต์เป็นจุดเริ่มฮุค
ส่วน range ที่เป็นขอบท่อนจริง ใช้ได้เฉพาะ start ไม่เอา end มาเป็นอีก occurrence
เก็บ origin ต่อ segment เพื่อไม่ให้คอมเมนต์ในผลรวมที่มี chapter ของ uploader
ถูกยกระดับเป็นขอบที่ uploader ระบุโดยผิดพลาด
แก้ส่วนกลาง ไม่มีชื่อศิลปิน/เวลาเฉพาะเพลงใน production parser

แล้วใช้จุดเสียงกลับเข้ามาเป็นหลักฐานต้นท่อน ต้องมีพลังงานลดลงจริงและฟื้นกลับชัดเจน
